# Portal File Chooser Integration — SPEC

## Overview

The Portal File Chooser integration replaces Qt's built-in FileDialog with a delegated D-Bus-based file picker provided by the xdg-desktop-portal service. This SPEC covers the implementation of a C++ portal client within the Viewer that integrates the D-Bus method `org.freedesktop.portal.FileChooser.OpenFile()`, handles Wayland parent window association via xdg-foreign, and provides a Qt FileDialog fallback when the portal service is unavailable.

The feature is scoped to:
- Replacing the primary Open path (Ctrl+O, menu item, empty-state button) with a portal request
- Integrating with the native file picker on the desktop environment (e.g., GTK, KDE, Nautilus)
- Preserving existing modal state and keyboard focus handling via `window.modalActive`
- Handling errors and missing portal services with a graceful Qt FileDialog fallback

---

## Non-Goals

- Multi-select file dialogs
- Save/SaveAs dialogs
- Folder selection dialogs
- OpenURI or other portal methods
- X11 parent-window handles
- Flatpak/document-portal path remapping (file:// URIs are opened directly)
- Holonight-qt provider or platform-theme dialog delegation
- Environment variable or configuration-file override of the portal path or fallback behavior
- Portal backend selection or negotiation
- Concurrent OpenFile requests (a second Open while one is outstanding is ignored)

## Glossary

| Term | Definition |
|------|-----------|
| xdg-desktop-portal | Desktop environment portal service; provides standard D-Bus interfaces for desktop operations (file selection, printing, screen capture, etc.) |
| FileChooser interface | D-Bus interface `org.freedesktop.portal.FileChooser` providing file and folder selection methods |
| OpenFile method | `org.freedesktop.portal.FileChooser.OpenFile()` method; takes a parent window, title, and options; returns a request handle |
| Request handle | Unique D-Bus object path (e.g., `/org/freedesktop/portal/desktop/request/<sender>/<handle_token>`) where the portal emits `Response` signal |
| Response signal | `org.freedesktop.portal.Request.Response` signal emitted when the user completes or cancels the picker |
| xdg-foreign | Wayland protocol extension (`zxdg_exporter_v2`) for exporting surface handles across clients |
| Exported handle | Opaque string delivered by `zxdg_exported_v2.handle`, passed to the portal as `wayland:<handle>` |
| handle_token | Unique per-request identifier generated by the caller to correlate the OpenFile call with the returned handle |
| modalActive | Boolean property on the Viewer window (`window.modalActive`) that blocks keyboard shortcuts and Open requests while a modal dialog or portal request is outstanding |
| Fallback dialog | Qt FileDialog shown only when the OpenFile call fails |
| Response code | Portal response exit code: 0 (selected), 1 (user cancelled), 2 (interaction ended another way, e.g. Escape or closing the picker) |

## Functional Requirements

### F.1 Portal Request Architecture

**REQ-F-001 (Ubiquitous — Portal Client Implementation)**

The Viewer shall implement a C++ portal client that sends D-Bus method calls to `org.freedesktop.portal.FileChooser.OpenFile()` on the session bus at bus name `org.freedesktop.portal.Desktop`, object path `/org/freedesktop/portal/desktop`.

**Acceptance Criteria:**
- A mock portal registered as `org.freedesktop.portal.Desktop` on the test session bus records exactly one `OpenFile` call on `/org/freedesktop/portal/desktop`, interface `org.freedesktop.portal.FileChooser`, per Open request
- No call is made to any `org.freedesktop.impl.portal.*` interface

**REQ-F-002 (Ubiquitous — Replace Primary Open Trigger)**

All Open triggers (Ctrl+O keyboard shortcut, "Open" menu item, empty-state button) shall use the portal client instead of the Qt FileDialog, with the Qt FileDialog available as a fallback.

**Acceptance Criteria:**
- The Loader at `Main.qml` lines 377–394 (currently loading FileDialog) is refactored to trigger a portal open request
- An automated test exercises the Ctrl+O shortcut and asserts a D-Bus OpenFile call is initiated
- The menu item and empty-state button follow the same code path (verified by code review or tracing)

### F.2 Portal Request Options and Filters

**REQ-F-003 (Ubiquitous — Filter List Construction)**

The portal OpenFile request shall send a `filters` option as a D-Bus array of filter specifications, each filter built from the existing `document.nameFilters` list using glob patterns (type 0).

**Acceptance Criteria:**
- The `filters` array is constructed as `a(sa(us))` (array of structs, each containing a string label and an array of (type, pattern) tuples)
- Glob patterns are extracted from `document.nameFilters` entries (e.g., "Image Files (*.jpg *.png)" → glob patterns "*.jpg" "*.png")
- Pattern type is 0 (glob) for all entries
- An automated test with a known `nameFilters` list asserts the constructed filters array has correct structure and content
- D-Bus mock captures the filters and verifies glob pattern accuracy

**REQ-F-004 (Ubiquitous — Current Filter Selection)**

The portal request shall send a `current_filter` option (`(sa(us))`) equal to the combined image filter entry built from the first `document.nameFilters` entry.

**Acceptance Criteria:**
- The mock portal records `current_filter` with signature `(sa(us))`
- The recorded `current_filter` is structurally equal to the first element of the recorded `filters` array

**REQ-F-005 (Ubiquitous — Current Folder Hint)**

When an image is currently open, the portal request shall send a `current_folder` option containing the NUL-terminated byte path of the folder containing that image.

**Acceptance Criteria:**
- If a document is open and has a local path, extract its directory path and encode as `ay` (byte array, NUL-terminated)
- If no document is open or the document is non-local, omit the `current_folder` option
- An automated test opens an image at `/tmp/test/image.jpg`, requests Open, and asserts `current_folder` is `/tmp/test` (NUL-terminated bytes)
- An automated test with no open document requests Open and asserts `current_folder` is absent from the options

**REQ-F-006 (Ubiquitous — Request Title and Handle Token)**

The portal request shall use the title "Open image" (translatable via `qsTr()` or `tr()`) and generate a unique `handle_token` for each request.

**Acceptance Criteria:**
- The title string is passed to qsTr() or tr() in C++ code for translation
- A unique handle_token is generated per request (e.g., using QUuid or a per-request counter)
- An automated test asserts the title appears in the D-Bus OpenFile call arguments
- Repeated requests generate distinct handle_tokens

**REQ-F-007 (Ubiquitous — Modal Flag)**

The portal OpenFile request shall include `modal: true` and `multiple: false` in the options.

**Acceptance Criteria:**
- The mock portal records `modal` = true and `multiple` = false (both `b`) in every OpenFile call

### F.3 Wayland Parent Window Association

**REQ-F-008 (Ubiquitous — Wayland Parent Export)**

Before calling OpenFile, the Viewer shall export the Wayland wl_surface of its main window using xdg-foreign (`zxdg_exporter_v2`) and pass the resulting handle as the parent_window parameter.

**Acceptance Criteria:**
- For each OpenFile request a new export is created (never cached, as the surface may be recreated)
- A unit test verifies that handle string `abc` is formatted as parent_window `wayland:abc`
- The export is destroyed when the request ends (response received, error, fallback triggered, or window closed); verified manually with `WAYLAND_DEBUG=1` (REQ-NF-011)
- Manual verification on Hyprland confirms the file picker window is parented to the Viewer

**REQ-F-009 (Ubiquitous — Fallback When Export Unavailable)**

If the platform is not Wayland, the compositor does not advertise `zxdg_exporter_v2`, or the export call fails, the Viewer shall still proceed with the OpenFile request using an empty string parent_window.

**Acceptance Criteria:**
- An automated test on the offscreen platform (QT_QPA_PLATFORM=offscreen) sends OpenFile with parent_window=""
- No console error or warning is emitted when export is unavailable; the request proceeds
- No fallback dialog is triggered solely because export failed (fallback only occurs if OpenFile itself fails or returns a non-file URI)

### F.4 Response Handling

**REQ-F-010 (Event-driven — Subscribe to Response Before Call)**

The Viewer shall subscribe to the `org.freedesktop.portal.Request.Response` signal on the predicted request object path before invoking OpenFile, to avoid race conditions.

**Acceptance Criteria:**
- A D-Bus signal connection is established on path `/org/freedesktop/portal/desktop/request/<sender>/<handle_token>` before the OpenFile call returns
- sender is the unique bus name of the Viewer (minus leading ':' and with '.' replaced by '_')
- The signal slot invokes a handler to process Response data
- An automated test on a mock portal that emits Response immediately after OpenFile confirms the signal is received

**REQ-F-011 (Event-driven — Re-subscribe to Returned Handle)**

If the OpenFile method returns a different handle than predicted, the Viewer shall immediately re-subscribe to the returned handle's Response signal.

**Acceptance Criteria:**
- The OpenFile D-Bus method signature returns an object path (handle)
- If the returned path differs from the predicted path, disconnect the old signal and connect to the new path
- An automated test returns a different handle and asserts the signal is re-subscribed
- A stale Response arriving on the old path is ignored

**REQ-F-012 (Event-driven — Successful File Selection)**

When a Response with code 0 is received with uris containing a file:// URL, the Viewer shall open that file through the existing document open path.

**Acceptance Criteria:**
- The Response signal carries a result dictionary with field `uris` (array of strings)
- If uris[0] starts with "file://", extract and percent-decode the path
- Pass the resulting local file URL to `window.document.open()` using the existing open flow
- Unicode, space, and percent-encoded paths are correctly round-tripped (e.g., "file:///tmp/caf%C3%A9.jpg" → local file `/tmp/café.jpg`)
- An automated test whose mock portal returns the percent-encoded `file://` URI of a fixture named with Unicode, space and `%` characters asserts the document reaches `Ready` with that fixture's dimensions
- A manual test selects a file with Unicode/space characters and verifies it opens

**REQ-F-013 (Event-driven — Non-File or Empty URI)**

When a Response with code 0 is received but uris is empty or contains a non-file:// URI, the document shall enter an error state with a user-visible message and no fallback dialog shall be shown.

**Acceptance Criteria:**
- An automated test with mock portal returning `uris: ["http://example.com"]` asserts an error message is displayed and no Qt FileDialog appears
- An automated test with empty uris asserts an error message is displayed
- The error message is translatable (uses tr() or qsTr())
- The error handling reuses existing document error state paths (no new error UI)

**REQ-F-014 (Event-driven — User Cancellation)**

When a Response with code 1 is received, the Viewer shall make no change to the current image, orientation, zoom, or keyboard focus target, and shall not show a fallback dialog.

**Acceptance Criteria:**
- An automated test opens an image, requests Open, sends a code-1 Response, and asserts the image, transform, and zoom remain unchanged
- The window.modalActive flag is cleared (reverting to false)
- No Qt FileDialog appears
- Keyboard shortcuts work again immediately after the Response
- Cancellation restores a previously focused visible, enabled control (not only
  the default neutral focus item); automated coverage exercises codes 1 and 2

**REQ-F-015 (Event-driven — Other Response Code / Interaction Ended)**

When a Response with code 2 (or any other non-zero code) is received, the Viewer shall handle it exactly as a code-1 cancellation (REQ-F-014) and shall not show the fallback dialog.

*Revised 2026-09-15 during manual acceptance (T-013):* xdg-desktop-portal-gtk 1.15.3 reports Escape and closing the picker window as code 2 with empty `uris`; only its Cancel button yields code 1. The original "code 2 → fallback" rule opened the Qt FileDialog after an ordinary Escape. Portal unavailability still reaches the fallback through REQ-F-016, because a missing service or backend fails the OpenFile call itself.

**Acceptance Criteria:**
- An automated test sends a code-2 Response with empty `uris` and asserts `cancelled` is emitted, no object named `openDialog` exists, and `modalActive` returns to false
- The document state is unchanged by a code-2 Response
- An unknown non-zero code is also handled as cancellation
- Manual acceptance: Escape in the GTK picker closes it without showing the Qt FileDialog

### F.5 Error Handling and Fallback

**REQ-F-016 (Event-driven — OpenFile Call Failure)**

If the OpenFile D-Bus method call fails (service not on bus, ServiceUnknown, UnknownInterface, UnknownMethod, any error reply, or timeout), the Viewer shall show the Qt FileDialog fallback exactly once.

**Acceptance Criteria:**
- An automated test with no portal service on the bus requests Open and asserts a Qt FileDialog appears with objectName="openDialog"
- An automated test with a portal service that rejects the OpenFile call (returns an error) asserts a FileDialog appears
- The fallback is shown exactly once per request (no retries)
- No second fallback is triggered if the user cancels the first one
- A console warning or debug log message records the portal error (but does not block the open flow)

**REQ-F-017 (Ubiquitous — OpenFile Timeout)**

The OpenFile D-Bus method call shall use an explicit timeout of 25 seconds before falling back to the Qt FileDialog.

**Acceptance Criteria:**
- The asynchronous OpenFile call is issued with a 25 000 ms timeout (default production value)
- The timeout is injectable for tests only (constructor/setter, not environment or config); an automated test with a mock that never replies and a shortened timeout asserts the fallback dialog appears once

**REQ-F-018 (Ubiquitous — Fallback Dialog Preserves Behavior)**

The fallback FileDialog shall preserve the existing behavior exactly: same title, nameFilters, accept/reject handling, and objectName="openDialog".

**Acceptance Criteria:**
- The fallback FileDialog is identical to the current FileDialog in Main.qml (lines 377–394)
- The fallback uses the same title (qsTr("Open image")), nameFilters, and onAccepted/onRejected handlers
- The objectName is "openDialog" for test identification
- An automated test exercises the fallback and asserts the same file is opened as with the current FileDialog

**REQ-F-019 (Ubiquitous — Portal Availability Probe on Every Request)**

Portal availability shall be probed on every Open request (no startup caching).

**Acceptance Criteria:**
- No portal availability result is cached; each Open request issues its own OpenFile call, whose success or failure is the probe
- An automated test stops the portal service between two Open requests and asserts the second uses the fallback
- No environment variable (e.g., XDG_DESKTOP_PORTAL) or config file override is supported; the code uses the standard D-Bus path

### F.6 Modal State and Request Lifecycle

**REQ-F-020 (State-driven — Modal Block During Outstanding Request)**

While a portal request (or fallback dialog) is outstanding, `window.modalActive` shall be true, blocking Viewer keyboard shortcuts and ignoring further Open triggers.

**Acceptance Criteria:**
- When OpenFile is called, window.modalActive is set to true before the call
- When the request finishes (any Response, error state, or the fallback dialog closes), window.modalActive is false
- An automated test asserts that Ctrl+O during an outstanding request does not initiate a second OpenFile call
- An automated test asserts that Escape and other shortcuts do not activate while modalActive=true (existing shortcut logic)

**REQ-F-021 (Event-driven — Request Close on Window Destruction)**

When the Viewer window closes or the portal client object is destroyed while a request is outstanding, the Viewer shall call `org.freedesktop.portal.Request.Close` on the request handle, release the xdg-foreign export, and never open a file from a later Response.

**Acceptance Criteria:**
- The portal client's shutdown path calls `org.freedesktop.portal.Request.Close` on the active handle if a request is outstanding; the mock portal records the call
- `Request.Close` is guaranteed once OpenFile has returned a handle; if the window closes before the handle is known, Close is sent when the reply arrives (best effort — nothing can be closed if the process exits first)
- The xdg-foreign export object is destroyed (`zxdg_exported_v2.destroy`)
- An automated test closes the window during an outstanding request and asserts Close is called
- Direct window destruction while the chooser survives also closes the request,
  both before and after the OpenFile reply; late responses are ignored
- An automated test closes the window, then receives a late Response, and asserts no file is opened

**REQ-F-022 (Event-driven — Ignore Superseded Responses)**

A Response arriving for a superseded or closed request shall be ignored.

**Acceptance Criteria:**
- A Response whose object path does not match the active request handle, or arrives when no request is active, changes no document or window state
- An automated test opens a file, closes the window (cancelling the request), then sends a Response on the old handle path and asserts no file is opened

**REQ-F-023 (State-driven — Outstanding Request Limitation)**

While the OpenFile call has returned a handle but no Response has arrived, the Viewer shall keep `window.modalActive` true, with no timeout, until a Response arrives or the window closes.

**Acceptance Criteria:**
- An automated test whose mock returns a handle but never emits Response asserts `modalActive` is still true and no fallback dialog exists after a wait longer than the (shortened) call timeout
- The limitation is documented in the Known Limitations/Risks section

### F.7 Accessibility

**REQ-F-024 (Ubiquitous — No Extra Announcement)**

No extra in-window announcement shall be emitted for the portal picker; it is a separate accessible window managed by the portal.

**Acceptance Criteria:**
- No new accessible item or announcement is added to Viewer's window for the portal request (code review + existing accessibility tests pass); manual Orca walkthrough recorded under REQ-NF-010
- After file selection or cancellation, existing load/error announcements behave as today (no change to document open announcements)

## Known Limitations and Risks

### Hyprland-Specific Limitation

**Native FileChooser Backend Dependency:** Hyprland's own native portal may not include a FileChooser implementation. If no GTK or KDE portal backend is configured via portals.conf (or if those packages are not installed), users will not see a native picker. In such environments, the fallback Qt FileDialog is the only available path. This is an environment configuration issue, not a Viewer limitation.

**Mitigation:** Document in release notes and manual verification that FileChooser backend must be installed and configured; provide example portals.conf snippets.

### Backend Behavior Variability

**Filter and current_folder Display:** Portal backends may ignore or alter the sent `filters`, `current_filter`, and `current_folder` options. Tests verify that these options are correctly sent (via mock D-Bus), but do not verify that GTK or KDE displays them as sent. Actual displayed behavior depends on backend implementation.

**Mitigation:** Manual testing records observed behavior on real backends (GTK/KDE); document any discrepancies.

### Timeout Latency

**25-Second Call Timeout:** If the OpenFile method call itself hangs (e.g. portal activation stalls), the Viewer will block modal state (window.modalActive=true) for up to 25 seconds before showing the fallback. During this time, Viewer keyboard shortcuts remain inactive. This is a deliberate trade-off: a shorter timeout risks false positives on slow systems; a longer timeout improves robustness at the cost of user-perceived lag.

**Mitigation:** Document the timeout value and fallback trigger in user-facing help; consider verbose debug logging to clarify what occurred.

### Non-Responding Backend

**Persistent Modal Block:** The call timeout covers only the OpenFile method reply. If the backend returns a handle but never sends a Response, window.modalActive remains true indefinitely (REQ-F-023). The user must close the Viewer window or kill the hung portal process to recover.

**Mitigation:** Recommend systemd service restart or Hyprland process management (hyprctl) to restart the portal service; document in troubleshooting guides.

### Surface Recreation Handling

**Wayland Surface Lifecycle:** If the Viewer's Wayland wl_surface is destroyed and recreated between OpenFile call and Response (e.g., after window state change, workspace switch, or compositor failure), the exported handle may become invalid. A new export is always created per request (not cached), but an in-flight request may refer to a stale surface.

**Mitigation:** Response handling checks if the Viewer window still exists before opening a file; per-request export lifecycle avoids caching stale handles.

## Appendix: D-Bus Method Signature Reference

```
org.freedesktop.portal.FileChooser.OpenFile (
    s parent_window,
    s title,
    a{sv} options
) -> (o handle)

Options:
  handle_token: s (unique per request)
  modal: b (true)
  multiple: b (false)
  filters: a(sa(us)) (array of filter label + pattern tuples)
  current_filter: (sa(us)) (one filter, same shape as a filters entry)
  current_folder: ay (optional; NUL-terminated path bytes)
  accept_label: s (not sent; use backend default)

Returned handle: o (D-Bus object path)

Response signal:
  org.freedesktop.portal.Request.Response (u code, a{sv} result)

  code: 0 = selected, 1 = cancelled, 2 = ended
  result:
    uris: as (array of file:// URIs for code 0)
    current_filter: (sa(us)) (optional, unused)
    choices: a(uss) (custom control choices, not used here)
```

## Appendix: xdg-Foreign Export and Parent-Window Format

```
Wayland interface: zxdg_exporter_v2 (xdg-foreign-unstable-v2)

Export a wl_surface to obtain an opaque handle:
  zxdg_exporter_v2_export_toplevel(surface) -> (zxdg_exported_v2)
  zxdg_exported_v2 emits ::handle(handle_string) — opaque string

parent_window format for portal:
  "wayland:<handle_string>"

  If export unavailable or fails, use empty string: ""
```
